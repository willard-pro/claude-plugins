# Bugs observed — 2026-06-02 (WIL-42 monitoring session)

## 1. HB heartbeat category corruption (data integrity)

Three entries in WIL-42's heartbeat log used `HB` as the category instead of `decision`/`gate`:

```
HB|decision|artifact-created|fired|created simple-fix|{"type":"simple-fix"}
HB|gate|coherence-check|ok|complexity-artifact match|...
HB|decision|regression-verdict|fired|ADJACENT|{"verdict":"ADJACENT"}
```

The bash functions (`hb_decision`, `hb_gate`) look correct — they pass proper categories to `hb_write`, and `hb_write` validates against `_HB_CATEGORIES` (would reject `HB`). Something in the EXEC agent's path is bypassing the bash helpers and writing directly. No `HB|` literal found in source — likely the sub-agent echoing directly rather than calling the functions.

**Impact:** Breaks heartbeat consumers (dashboard, overseer, retro). Heartbeat format spec declares 7 valid categories; `HB` is not one of them.

## 2. Implement phase writes zero step entries (observability gap)

WIL-42 implement: 7-min dead zone, then `IMPLEMENT|implement|done|Smooth`. 118k tokens in, 19k out — real work happened, but zero intermediate step entries. No `load-plan`, `make-changes`, `lint-check`, `commit-push`, or `create-pr` entries.

Same sparse logging in MAINTENANCE: `document|done` appeared without a preceding `document|start`.

**Impact:** Pipeline log is the checkpoint mechanism and observability source. Missing steps mean crash recovery can't resume mid-phase and overseer/dashboard see a 7-min dead zone.

## 3. merge-decision hangs on CONFLICTING PR (resilience gap)

WIL-42 PR conflicted with WIL-39 in `worker/triage/inbox.py`. PR showed `mergeable: CONFLICTING, mergeStateStatus: DIRTY`. The agent sat for 7 minutes resolving it — zero pipeline log entries during that time. Resolution eventually succeeded (PR merged), but there's no timeout, no progress logging, and no fallback if it can't resolve.

**Impact:** If the conflict can't be auto-resolved, the pipeline hangs until the orchestrator's pinger timeout (80 × 90s = 2 hours max). No human notification in the interim.

## 4. Zombie spawn_agent_pre processes (resource leak)

Command substitution `$(spawn_agent_pre ...)` forks subshells that never get reaped. Each agent spawn leaves 2 processes behind. After 3 phases, 6 zombies visible via `ps aux | grep WIL-42`. Causes:
- Pinger chaos (multiple pinger processes with conflicting counters: 9→18→4→13→10→19→0→15)
- Dual watchdog pings 2s apart (two watchdog loops running)

**Fix:** Add `wait` for child processes after command substitution, or use process group kill in spawn cleanup.

## 5. Implement doesn't create PR (workflow gap)

Agent committed and pushed `feature/WIL-42-inbox-cursor-class-poll-inbox-integration` to ledgerly but didn't open a PR. PR-REVIEW phase had to `find-pr` — initially found the wrong PR (claude-plugins#29, same PR number) before correcting to ledgerly#29 by branch name. The review comment landed on the correct PR, but the initial misroute is fragile.

**Impact:** Adds friction to PR-REVIEW phase. The `find-pr` step relies on branch-name matching — if implement used a different branch naming convention, the PR would be unfindable. Potential for commenting on wrong PR (same number in different repo).

## Fleet controller findings (ticket-fleet-controller skill review, 2026-06-02)

Cross-reference audit against pipeline internals (flow.sh, heartbeat.sh, retro.sh `jq -n` bug trace).

### Bug #F1: Lockfile path mismatch — `_flow_mutex_held()` dead code (CRITICAL)

`fleet-intervene.sh:29` checks `/tmp/ticket-auto-${tid}-flow.lock` by reading a PID and `kill -0` testing it. `flow.sh:34` uses `./logs/.ticket-flow-${TICKET_ID}.lock` with `flock -n -E 42` (kernel fd-based lock). These are completely different files in different directories with different locking primitives.

```
fleet-intervene.sh:  /tmp/ticket-auto-WIL-42-flow.lock   → kill -0 $(cat file)
flow.sh:             ./logs/.ticket-flow-WIL-42.lock       → flock -n -E 42 fd 9
```

`_flow_mutex_held()` returns 1 (mutex not held) 100% of the time. Fleet controller can kill a pipeline while flow.sh is mid-mutation on Linear.

**Fix:** Change `_flow_mutex_held` lockfile path to `./logs/.ticket-flow-${tid}.lock` and use `flock -n` (non-blocking try-lock) instead of PID check. Path must be relative to working directory, mirroring flow.sh.

### Bug #F2: Same `jq -n` missing `-c` pattern as retro.sh (MODERATE)

`fleet-detect.sh:414,436,444` — three `jq -n` calls without `-c`. Same root cause as the retro.sh `jq` parse error fixed earlier today. Currently safe because results are consumed via `--argjson` (which handles multi-line JSON), but it's the same trap: any future code that processes these values line-by-line with `while read` will produce doubled commas and broken JSON.

```bash
# fleet-detect.sh:414 — multi-line output, consumed via --argjson (currently safe)
entry=$(jq -n --arg tid "$tid" ... '{tid: $tid, ...}')  # ← missing -c

# fleet-detect.sh:436 — same pattern
summary=$(jq -n --argjson total "$total" ... '{total: $total, ...}')  # ← missing -c

# fleet-detect.sh:444 — same pattern
jq -n --argjson pipelines "$results" ... '{pipelines: $pipelines, ...}')  # ← missing -c
```

**Fix:** Add `-c` to all three. The final output at line 444 may intentionally be pretty-printed (human-readable), but the internal ones at 414 and 436 should be compact.

### Bug #F3: `_last_field` has same `cut -f5` truncation pattern (MODERATE)

`fleet-detect.sh:52-59` — `_last_field` uses `awk -F'|' -v n="$idx" '{print $n}'`. For field 5+ (MSG), this truncates at embedded `|` — the exact bug documented in `pipeline-log-fragility.md` memory. Contrast with `_last_msg` (lines 67-74), which correctly joins fields 5+ through NF.

Currently `_last_field` is only called with field index 2 (phase name), which is safe. But the function signature (`_last_field <file> <idx>`) invites misuse — nothing stops a caller from passing 5.

**Fix:** Add safety comment or assert `idx < 5`, or merge into `_last_msg` and remove `_last_field` entirely.

### Bug #F4: No heartbeat `retry`-fail detection — flow.sh failures invisible (CRITICAL)

None of the 5 fleet detectors scan heartbeat logs for `retry|flow-sh|fail` entries. The retro.sh trace shows real failures across three tickets:

```
WIL-39:  flow.sh appraise-start failed (exit 2)
WIL-39:  flow.sh human-approve failed (exit 2)
WIL-39:  flow.sh implement-outcome failed (exit 2)
WIL-38:  flow.sh appraise-start failed (exit 2)
WIL-25:  flow.sh implement-complete failed (exit 127)
```

`detect_phase_failures` only reads pipeline logs. `detect_loops` counts `loop-back` events, not `retry`. A pipeline that silently fails every trigger dispatch would show as "healthy" (severity 0) in the fleet dashboard.

**Fix:** Add a 6th detector `detect_flow_failures` that scans `${tid}-heartbeat.log` for `retry|flow-sh|fail` entries. Escalate based on count: 1 failure → WARN, 2+ → KILL.

### Gap #F5: Restart spawn is a no-op (MODERATE)

`fleet_restart_pipeline` prints `RESTART_ELIGIBLE=<tid>` to stdout but doesn't spawn anything. The SKILL.md monitor loop at lines 106-112 reads severity and calls `fleet_restart_pipeline`/`fleet_kill_pipeline`, but doesn't capture `RESTART_ELIGIBLE` or spawn a new agent. The restart path silently does nothing beyond writing log entries.

```bash
# SKILL.md:106-112 — reads severity, calls functions, but restart output is lost
echo "$data" | jq -r '.pipelines[] | select(.severity >= 2) | ...' | while read -r tid sev; do
  if [ "$sev" -eq 3 ]; then
    fleet_restart_pipeline "$tid" "auto-restart" ./logs || true  # ← prints RESTART_ELIGIBLE, nobody reads it
```

**Fix:** Either capture `RESTART_ELIGIBLE` and spawn a Claude Code agent for `/ticket-auto ${tid} --auto`, or move the spawn into `fleet_restart_pipeline` itself.

### Gap #F6: `fleet_kill_pipeline` no pre-kill existence check (LOW)

`_log_pipeline` calls `mkdir -p` — so `fleet_kill_pipeline NOEXIST-99 "test"` creates a fresh pipeline log directory and writes outcome entries for a ticket that never had a pipeline. No validation that the pipeline log existed before intervention.

**Fix:** Guard with `[ -f "$log_file" ] || { echo "no pipeline log for ${tid}"; return 1; }` before writing.

### Gap #F7: `FLEET_AUTO_RESTART=false` severity display mismatch (LOW)

When auto-restart is disabled, detection still returns severity 3, dashboard still shows `💀 RESTART`. The degradation to KILL only happens at intervention execution time (in `fleet_restart_pipeline`). Operator sees RESTART severity but nothing restarts — confusing.

**Fix:** `fleet_detect_all` should cap max severity at 2 when `FLEET_AUTO_RESTART=false`, or add a separate `effective_severity` field.

### Gap #F8: No time-window filter — stale logs persist forever (LOW)

Unlike `retro.sh --window 7d`, the fleet controller scans ALL pipeline logs regardless of age. Orphaned logs from weeks ago appear as abandoned/stalled permanently with no expiration.

**Fix:** Add `FLEET_MAX_LOG_AGE_HOURS` config — skip pipeline logs older than N hours in `fleet_detect_all`.

### Gap #F9: heartbeat.sh not sourced — audit trail silently skipped (LOW)

`fleet-intervene.sh:97-100,173-176` guards `hb_decision` calls with `declare -f hb_decision >/dev/null 2>&1`. But neither `fleet-intervene.sh` nor `fleet-dashboard.sh` source `heartbeat.sh`. SKILL.md doesn't mention sourcing it. Result: fleet kill/restart heartbeat audit entries are silently skipped unless the caller happened to source heartbeat.sh first.

**Fix:** Add explicit `source` of heartbeat.sh in `fleet-intervene.sh`, or document the requirement in SKILL.md. Same pattern as the spawn-helper.sh → heartbeat.sh source fix from earlier today (PR #50).

### Gap #F10: Race window — kill during active agent spawn (LOW)

Fleet controller touches `/tmp/ticket-auto-${ID}-pinger-stop`. Pinger checks this at iteration top, exits cleanly. But orchestrator's main loop doesn't check between `spawn_agent_pre` and waiting for agent completion. If fleet kills during that window: pinger stops, orchestrator is already past the check, agent spawn completes, `|waiting|` entry gets written AFTER `|outcome|` — creating a zombie entry post-outcome.

**Fix:** Document in SKILL.md as known edge case. Mitigation: `spawn_agent_pre` could check stop file before writing `|waiting|`. Or fleet controller could wait 1 poll cycle after kill before declaring outcome.
