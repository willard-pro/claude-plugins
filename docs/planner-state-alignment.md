# Planner → Ticket-Auto State Alignment

> Documents how the ticket-planner's 12-phase state machine maps onto ticket-auto's pipeline states and the Linear label/state contract that bridges them.
> Written 2026-07-24 as Part 7 integration wiring.

## The two state machines

ticket-planner and ticket-auto run **different state machines on different entities**. The planner operates on initiatives (ideas → plans → generated tickets). ticket-auto operates on individual tickets (investigate → implement → verify → merge). They communicate through Linear labels and a structured markdown block, not through direct state coupling.

### Planner states (12 phases)

```
Appraisal → Discovery → Architecture → Proposal → Review → Consensus →
OpenSpec → Epic Gen → Story Gen → Ticket Gen → Execution → Completed
```

Each phase runs as an isolated Claude agent. State lives in `${REPOS_ROOT}/.ticket-auto/initiatives/{ID}/state.log`. The router is bash — it reads the log, derives position, and dispatches phases.

### Ticket-auto states (pipeline)

```
APPRAISE → EXEC → GATE → IMPLEMENT → VERIFY → PR-REVIEW → MAINTENANCE
```

State lives in `${TICKET_DIR}/pipeline.log`. The thin router (`/ticket-auto`) reads the log, derives position, and dispatches phases.

## Handoff: planner → ticket-auto

The planner does not directly invoke ticket-auto. The handoff is indirect, through Linear:

1. **Planner creates tickets** with `planned` label + `## Planner Context` block + `Backlog` state
2. **Fleet controller detects** the initiative epic (`state:execution`) with undispatched planned children
3. **Fleet dispatches** eligible children (respecting `blocked-by`, priority, concurrency) → spawn queue
4. **fleetd spawns** a worker running `/ticket-auto {TID} --auto --from-planned`
5. **ticket-auto consumes** the Planner Context block during appraise (fast-path for planned)

The planner never touches ticket-auto's state. ticket-auto never touches the planner's state. They share only the Planner Context block and labels on the Linear ticket.

## Label bridge

| Label | Set by | Read by | Meaning |
|-------|--------|---------|---------|
| `planned` | Planner (Ticket Gen) | ticket-auto (appraise), fleet (dispatch filter) | Provenance marker — ticket generated by planner. Never removed. |
| `INIT-{id}` | Planner (Ticket Gen) | Fleet (dispatch grouping), feedback (initiative aggregation) | Links ticket to its initiative. Never removed. |
| `pre-approved` | Planner (Ticket Gen), when confidence ≥ 0.85 | ticket-auto (fast-path eligibility) | Accelerates appraise. Removed by `human-reject`. |
| `blocked-by:{ID}` | Planner (Ticket Gen) | Fleet (dispatch skip) | Dependency enforcement. Auto-removed when blocker reaches Done. |
| `state:execution` | Planner (Execution phase) | Fleet (detection trigger) | Initiative ready for dispatch. On the EPIC, not child tickets. |
| `Type` (`bug`/`feature`/`improvement`/`security`/`chore`) | Planner (Ticket Gen) | ticket-auto (template selection at gate 2.7b) | Drives body template. Never removed. |

## State alignment table

| Planner phase | What it produces | Ticket-auto equivalent | Relationship |
|---------------|-----------------|----------------------|-------------|
| Appraisal | Initiative scope, repo list | APPRAISE (investigation) | Planner Appraisal = initiative-level. ticket-auto Appraise = per-ticket. |
| Discovery | Code paths, symbols, API contracts | APPRAISE (codebase grep) | Planner Discovery replaces ticket-auto's codebase grep for planned tickets. |
| Architecture | Technical approach, ADR | EXEC (artifact creation) | Planner Architecture = initiative-level design. ticket-auto EXEC = per-ticket implementation plan. |
| Proposal | `proposal.md` | — | No ticket-auto equivalent. The proposal lives in the planner's artifact plane. |
| Review | Critique findings | — | Internal planner quality gate. Analogous to ticket-auto's GATE but at initiative level. |
| Consensus | Finalized plan | — | Settled plan before spec generation. |
| OpenSpec | Spec artifacts | EXEC (openspec change creation) | Planner OpenSpec = initiative-level specs. ticket-auto EXEC = per-ticket simple-fix or openspec apply. |
| Epic Gen | Linear epic + `state:execution` | — | No ticket-auto equivalent. Creates the parent entity. |
| Story Gen | Story descriptions | — | May collapse into Ticket Gen. |
| Ticket Gen | Linear tickets + Planner Context + labels | — | Output consumed by ticket-auto. This is the handoff point. |
| Execution | `state:execution` label on epic | — | Handoff trigger. Fleet detection picks up from here. |
| Completed | Terminal state | MAINTENANCE (terminal) | Both are terminal. Planner Completed = initiative done. ticket-auto MAINTENANCE = ticket done. |

## Confidence flow

```
Planner confidence (0.0–1.0)
  → Planner Context block (Confidence field)
  → planned-ticket-check.sh validates (exit 2 if low confidence + not pre-approved)
  → appraise fast-path: skips codebase grep if planned + valid + confidence ≥ threshold
  → gate check 2.7: context validation (+ depth mismatch warning)
  → post-implement: planned-feedback-write.sh emits confidence_actual vs confidence_predicted
  → fleet-feedback.sh aggregates drift per initiative
  → planner re-plan: Regenerate flag → reads feedback → adjusts confidence
```

## Planner Context block (the contract surface)

The `## Planner Context` block in ticket descriptions is the only data that crosses the planner→ticket-auto boundary. Fields:

| Field | Version | Required | Used by |
|-------|---------|----------|---------|
| Schema-Version | 1+ | Yes | Validator (accepts 1 or 2) |
| Initiative | 1 | Yes | Fleet dispatch grouping |
| Epic | 1 | Yes | Fleet dispatch parent validation |
| Confidence | 1 | Yes | Appraise fast-path, gate check |
| Strategy | 1 | Yes | Appraise context |
| Decision | 1 | Yes | Appraise context |
| Affected Services | 1 | Yes | Appraise fast-path (scope narrowing) |
| Target Symbols | 1 | Yes | Appraise fast-path (code location) |
| Pre-approved | 1 | Yes | Gate check (fast-path eligibility) |
| Generated | 1 | Yes | Freshness check |
| Regenerate | 1 | Yes | Re-plan trigger |
| Exploration Depth | 2 | No | Appraise investigation depth |
| Code Paths Traced | 2 | No | Appraise code location |
| API Contracts Analyzed | 2 | No | Appraise API scope |
| Alternative Approaches | 2 | No | Appraise design context |
| Open Questions | 2 | No | Appraise investigation gaps |

Schema-Version 2 is backward-compatible — all new fields are optional. Validator (`planned-ticket-check.sh`) accepts both versions.
